# Shared operation contract

Per-operation arguments, defaults and runnable examples, generated from `src/kurtshape/operation_schemas.py`: [OPERATIONS.md](OPERATIONS.md).

The authoritative document is native FreeCAD FCStd. A feature object's `Name` is its stable ID; native Sketcher constraints are parameters and native expressions are dependencies. `KurtShapeProject` stores project UUID, opaque revision, build status and source mapping, without duplicating editable geometry or dimensions. Studio operations additionally persist an ordered native feature list and logical part identities. Body resolution uses explicit `body`, the target/support's owning Body, or the sole current part. Several eligible parts without a target or explicit ID reject with `ambiguous_body`; assistants never inherit GUI focus. Historical and auxiliary Bodies are native dependencies and are excluded from current results.

`Controller.dispatch(request)` returns `{ok:true,result}` or `{ok:false,error:{code,message,...}}`. Successful document operations return inspection including `document_id`, `revision`, native features, `build_status`, measurements and `active_sketch_edit`. Mutations run serially on the GUI thread; the interface does not transport arbitrary executable code.

Create/open requests are `{op:"new",name:"Plate"}`, `{op:"open",path:"absolute.FCStd"}` and `{op:"import_step",path:"absolute.step"}` (also `.stp`, case insensitive). These create/select documents without an existing document/revision. Existing-document operations require `document_id`; every mutation, including undo/redo, sketch lifecycle, rebuild, save and export, also requires current `expected_revision`. Inspect requires no revision. Tokens are UUIDs rather than counters. Native modeling edits, undo/redo and reopen invalidate older tokens; stale requests reject before mutation.

## Face selection and feature history (GUI, 2026-10-20)

In an idle Part Studio, selecting a bounded face highlights its last modifier
as the feature tree's selected/current row. Tree signals are blocked so the
native face remains selected; there is no “Last modifier” label or badge. This
does not open an editor, change the active part, create an Undo step or modify
the document. Ctrl multi-selection highlights each distinct modifier;
clearing/removing picks updates the rows. Hover does not navigate history.
A feature filter is preserved; **Reveal** explicitly clears it when needed.
Active tools, sketch/reference/section picking and native Tasks keep priority.

Last modifier means the latest operation in model order that changed the
complete bounded face, including trimming holes/boundaries, splitting and
merging. Unchanged faces pass through later operations to their earlier
modifier. This differs deliberately from the `created_by` selector, whose
creator semantics are unchanged. The read-only resolver uses recorded native
predecessor solids and verifies complete bounded-face and boundary-curve
equivalence, with a 1e-7 mm linear tolerance. Unsupported, stale or ambiguous
history leaves the feature unhighlighted instead of guessing.
Imported bases identify their import with earlier history unavailable;
assembly snapshots do not imply access to source feature history. No new
bridge operation or contract revision is introduced.

See [the design and implementation record](face-feature-selection/DESIGN_BRIEF.md).

## Contract 3.0 — Q03 lightweight status and explicit checks

Q03 published `contract:3` and `contract_revision:0`; the [3.1 additions](#contract-31--fail-fast-studio-results-typed-helices-and-tight-boxes) publish `contract_revision:1`. Local validation passed 187 native, seven bridge and 22 shortcut cases plus 415 workflow checks; the full GUI sweep retained seventeen passes and its recorded carrier-history exception, and the status recipe passed seventeen checks. Paired five-repeat benchmarks and independent plate confirmation are recorded in the [Q03 record](architecture-responsiveness-upgrade/STATUS_REPORT.md#validation-and-source-versions), including open absolute targets. Revision, replay, ownership, write-root and native transaction guards retain their earlier semantics. The historical contract-2 records below describe their own increments.

Every request accepts optional `measure`, exactly JSON `false`, `true` or the string `"full"`. Omission defaults to `true`; explicit null, numeric 0/1 and other strings reject with `invalid_argument`. The field participates in canonical replay identity, including omission versus an explicit value. Direct Python `Controller.inspect(doc, measure=None)` uses the controller default; wire null is not that shortcut.

| Level | Measurements on a current solid result |
|---|---|
| `false` | `solid_count`; `volume_mm3`, `area_mm2`, `bbox_mm` and `center_of_mass_mm` are null |
| `true` | Solid count, volume, area and bbox; centre of mass is null |
| `"full"` | Solid count, volume, area, bbox and volume-weighted centre of mass |

`bbox_mm` is the exact (tight) box of the geometry since 3.1, not FreeCAD's control-point box; see [tight boxes](#contract-31--fail-fast-studio-results-typed-helices-and-tight-boxes). `measurements.valid` is independently null until an explicit or export geometry check is cached, then reflects that verdict at any level. Aggregate and per-result `geometry_check` are `not_checked`, `valid`, `invalid` or `not_applicable` when there is no solid. Failed or unrecomputed intent has `measurements:null` and separately labeled `retained_geometry_measurements` at the requested level. `build_status:"valid"` means the native build/status checks succeeded; it does not imply BRepCheck ran.

`check_geometry` is read-only and requires `document_id`, with optional `body` identifying a current result or logical part. It checks selected/all current solids, returns inspection plus `geometry_check_report:{status,revision,engine,bodies,ms}`, and reports each body's `id`, `valid`, `issues` and `check_ms`. No solid rejects with `no_solid`. It reuses a source-shape verdict without changing revision, geometry or native history. Export first requires a current build, then performs/reuses valid geometry checks before staging output/provenance; an invalid verdict rejects with `invalid_geometry`.

The GUI sends `measure:false` on ordinary inspection/dispatch and displays solid count. **Check geometry** runs explicitly with a wait cursor and per-part Messages; **[ / Measure** measures selected geometry or requests full active-part mass properties without replacing the lightweight panel state. Measurement requests alone never run BRepCheck.

Transient geometry facts use the native object's own version, source Shape hash and source/occurrence placement dependencies. Shape-only versions key validity, so rigid placement changes invalidate world measurements without checking unchanged source topology. Each controller retains at most 1024 check verdicts and 4096 scalar/pair memo entries; eviction recomputes the same native result, and document close removes its data. Exact U2 common-volume/distance work follows conservative bbox rejection and caches exact parameters/frames/subelements; closest selectors retain all ties. Ordinary status reads cached health and cheap native-input/pending-scope diagnostics. Managed recompute and explicit open fill scope diagnostics; sync consumes a recorded external native recompute once for read-only selector/scope reconciliation. Native observer callbacks only mark boundaries, and idle status performs no exact scope boolean or selector evaluation.

Stored managed Part Studios already using `UseHasher=false` open without native recomputation. A true-hasher managed attachment switches mode and recomputes once. Native Assembly reopen retains its existing solve/recompute path, and recovery retains its reconstruction path. Engine stamps and native saved ProgramVersion produce `engine_changed`, `saved_by_other_build` or `engine_unrecorded`; absent expected stored shapes produce `missing_shapes`. Stored failed/Touched flags remain failed/unrecomputed. Retained geometry remains available for inspection, while export requires explicit Rebuild. Rebuild stamps the current engine in the same native undo step; Undo restores the old reason/stamp. Input archives are not rewritten on open.

Entity coordinates are sketch-local millimeters. Supported dimensional constraints are Distance, DistanceX, DistanceY, Diameter, Radius and Angle; angles use radians. Unnamed dimensions use keys such as `Constraints[17]`. Numeric values must be finite and satisfy native dimensional/solver validation. Source-created features may carry optional request fields `source_feature_id`/`source_feature_name`, stored in native source properties and metadata mapping.

The GUI starts a lease before native `setEdit`. Stop active drawing tools, call native `resetEdit`, then finish or cancel through the controller. During the lease, only that sketch's geometry/parameter/reference/support changes, inspect, managed undo/redo and finish are permitted. Refresh inspect after native edits. Native construction tools may commit intermediate transactions; finish groups lease transactions and cancel restores the initial sketch without deleting prior history or allowing canceled geometry to return through redo. Closed-document leases cannot survive same-UUID reopen. See [native sketch plane and lifecycle details](SKETCH_PLANE_CONTRACT.md).

Managed legacy documents retain `KurtShapeFeatureOrder` as native chronological links without enabling multi-part behavior. Native Undo may recreate deleted features in a different allocation order; the feature history and rollback sequence continue to use the accepted chronological links. `Controller.delete_features_plan(doc, features, body=None)` is a read-only GUI helper returning ordered `selected`, unselected `dependents` and total `removed` IDs, with the same target/dependency validation as deletion.

Standalone modeling failures abort their transaction and retain accepted geometry/revision. A failed managed command restores its pre-command draft; failed Finish retains the full current draft/lease and advances the revision. The GUI reopens Sketcher and shows the error in Messages. Only explicit Cancel discards the lease. Native failed builds report explicit errors; unrecomputed touched features report `needs_rebuild`, `measurements:null` and separate `retained_geometry_measurements`. Export rejects failed or unrecomputed builds. Retained geometry is not a successful evaluation of new intent.

## Contract 3.1 — fail-fast studio results, typed helices and tight boxes

October 17 contract 3.1 publishes `contract_revision:1`. The changes are additive, except that some studio results accepted before now reject (below) and `bbox_mm` is tighter on curved parts. They came from a scripted step drill whose helical flute cuts failed silently while `build_status` stayed `valid`. Evidence: `tests/test_result_checks.py` (11 native cases), whose self-contained Zimmer step-drill body reproduces both failures on FreeCAD 1.1.4 / OCCT 7.8.1.

**Result post-conditions.** Studio Extrude/Remove (`pad`/`pocket`), `revolve`, `sweep`, `loft` and `extrude_face` with `operation:"add"|"remove"|"intersect"` verify each result before accepting it, in this order:

1. Native success and one solid per scoped part, otherwise `build_failed`.
2. BRepCheck `isValid` of each result, otherwise `invalid_geometry` with `check:"brepcheck"` and `issues`.
3. A tool solid with positive volume, otherwise `invalid_geometry` with `check:"tool"` (empty or inside-out tool).
4. Volumes a Boolean of that kind can give, otherwise `invalid_geometry` with `check:"volume"`: Remove keeps each part within [before − tool, before], Intersect within [0, min(before, tool)], Add within [max(largest input, tool), inputs + tool], each with a slack of 1e-6 × (inputs + tool) mm3.
5. The tight result box inside the input part's box (Remove; Intersect also inside the tool's box) or inside the box of inputs and tool (Add), allowing max(1e-3 mm, 1e-6 × box diagonal); otherwise `invalid_geometry` with `check:"bounds"`, `outside_mm`, `bbox_mm` and `allowed_bbox_mm`.
6. A Remove must take more than a negligible volume from at least one scoped part (`empty_cut`, with `parts` and `tool_volume_mm3`). An Add with one target must add more than that (`empty_add`); Adds that merge several targets are not checked for emptiness. Negligible is max(1e-7 mm3, min(1e-6 × part volume, 1e-5 × tool volume)). OCCT's volume of curved (BSpline) solids carries noise near 1e-7 of the part volume, so Pocket's absolute 1e-7 mm3 alone cannot tell a cut that OCCT silently missed from a real one: the missed flute "removed" −0.0004 mm3 from a 7647 mm3 drill body.

A failed OCCT Boolean can pass BRepCheck. A refined second helical flute took its whole tool volume and grew 2.5 mm past the Ø13 step (cut inside out) while `isValid` held; checks 4 and 5 exist for that. Every rejection names the operation in `feature` (its requested `id`) and the affected `part`, and rolls back like any failed command.

Success adds `result_report` to the response: `feature`, `operation`, `tool_volume_mm3`, `volume_delta_mm3` (sum over parts, negative for removed material), `parts:[{part, body, volume_before_mm3, volume_after_mm3, volume_delta_mm3}]` (an Add's row also lists `merged_parts`), `geometry_check:"valid"`, `check_ms` and `refine` (below). `preview` runs the same checks and returns the same `result_report`, or `valid:false` with the error and its details (preview errors now carry the details of every rejection).

- **Cost.** One BRepCheck and a few exact boxes per result, about 0.2 s per flute on the drill. Before 3.1, accepting these studio operations ran no BRepCheck; GUI Extrude/Remove/Revolve acceptance now runs this one check per result as well.
- **GUI live preview.** The Extrude/Remove dialog's live preview skips BRepCheck, the bounds check and the empty-Add check (it shows a reversed Add's tool on the unchanged part) and keeps the native, volume and empty-Remove checks. Acceptance through dispatch runs them all.
- **Caching.** The verdict is not cached: `measurements.valid` and `geometry_check` keep their meaning until `check_geometry` or export. Since contract 3.2 (§3.2.1) the result post-conditions themselves are keyed by content and re-run for affected operations on every managed change; `geometry_check` keeps its meaning.
- **Scope.** Checks run when the operation is created and, since contract 3.2 (§3.2.1), for every result operation a managed edit, sketch lease, preview or batch affects, at its own history position; rebuild, rollback, undo/redo and native edits expose failures without rejecting; export validates pending operations. `operation:"new"`, part patterns, `boolean_parts`, `split_part` and `move_face` are unchanged.

**Refine.** The same operations take `refine` (boolean, default `true`). It sets native `Refine` on the result's `PartDesign::Boolean`s and on the operation's input snapshot `SubShapeBinder`s, since each snapshot refines its input part again. Before 3.1 both were always true.

- **Automatic retry.** When a refined result fails any post-condition, the operation retries once with both unrefined. Success then reports `refine:{requested:true, applied:false, retried_unrefined:true, refined_failure:{code, message, check, part, issues}}`. Failure returns the unrefined attempt's error with `refine:{requested, retried_unrefined, refined_failure, hint}`. Without a retry the report is `{requested, applied, retried_unrefined:false}`.
- **Helical cuts.** Refining merges the per-turn faces of a helical cut into multi-turn faces, which the next Boolean misses or turns inside out. Pass `refine:false` for helical cuts. A refined earlier result can make a later cut fail even unrefined; the `hint` says so.
- **Persistence.** The native `Refine` values persist and managed rebuilds keep them. An automatic-scope migration gives new inputs and results the representative Boolean's `Refine`.
- **Rejections.** A non-boolean value rejects with `invalid_argument`. `refine` with `operation:"new"` is accepted and has no Boolean to act on. A legacy `pad`/`pocket` without `operation` or `merge_scope` rejects `refine` with `invalid_argument`.

**create_helix.** A native top-level `Part::Helix` usable as a `sweep` `path` (row in the [Part Studio table](#u2-part-studio-and-reference-queries--october-2)).

- **Frame.** The helix starts at origin + radius · (cos a · x + sin a · (axis × x)), with a = `start_angle` and x = `x_direction`, and rises along `axis.direction`. A right-handed helix turns counter-clockwise seen from the axis tip.
- **Segments.** Each `segment_length` turns form one edge (native `SegmentLength`). An undivided multi-turn helix (native default 0) gives sweep faces that OCCT Booleans silently miss, which 3.1 rejects as `empty_cut`; hence one turn per edge by default. At most 1000 turns and 1000 edges.
- **History.** The helix enters the feature history like a sketch. It does not enable the Part Studio, so the document's Body defaults stay. A sweep keeps it as an input, never as its own helper, and the GUI hides it when a sweep consumes it. `delete_features` removes it; while a sweep uses it, deletion rejects with `external_dependency` unless the sweep is selected too.
- **Inspection.** The feature row adds `helix:{pitch_mm, height_mm, radius_mm, turns, handedness, segment_length_turns, edge_count, axis:{origin,direction}, start_direction, start_point_mm, start_tangent, end_point_mm}`. A profile perpendicular to the path at its start is `create_plane` with `origin:start_point_mm`, `normal:start_tangent`.
- **Editing.** `Pitch`, `Height` and `Radius` are `set_parameter`/`set_expression` parameters (mm). `set_parameter` keeps the turn and edge limits. Since 3.2 the same limits apply to formulas: `set_expression` and a parameter edit that changes a helix formula check the formula's value before any rebuild (`invalid_argument`) and again after it.

**Tight boxes.** `bbox_mm` in measurements and in export provenance is OCCT's optimal box of the exact geometry (`Shape.optimalBoundingBox` without triangulation or shape tolerance), so it no longer encloses BSpline control points. The fluted drill measures 13.0 mm across instead of 28.8 mm. The value is the same in the GUI and headless. It can exceed the exact extent by about 1e-7 mm on analytic faces and 5e-5 mm on swept BSpline faces. Selectors and scope pruning keep FreeCAD's faster native box, which is always conservative. A shape OCCT cannot box falls back to the native box. Exact boxes cost time on large curved models (about 0.2 s for the 65-face drill) and are cached like the other measurements.

### 3.2.1 Result checks on edits and rebuilds

Owner U3 (`src/kurtshape/result_checks.py`, spec `runtime/contract-3.2/specs/validation.md`). The 3.1 post-conditions of a studio result (one valid solid per output part, BRepCheck, volume delta against the tool volume, tight-box reach, non-empty Add/Remove/Intersect) no longer run only at creation: every managed change re-runs them for the result operations it affects, at each operation's own history position, and rejects the change with the creation codes when a result would fail.

**Result operations.** An active or held studio operation recorded as `pad`, `pocket`, `revolve`, `sweep` or `loft` (`extrude_face` records `pad`) with `operation` `add`, `remove` or `intersect` and a neutral tool Body. `operation:"new"`, patterns, `boolean_parts`, `split_part`, `move_face` and transforms are not result operations; their downstream result operations are still validated. `capabilities.result_checks` lists `operations`, `kinds`, `validated`, `exposed_only`, `interactive`, `export`, `persisted` and `checker`.

**Keys and verdicts.** Each result operation has a content-addressed key: a Merkle digest of the native intent of its input closure (geometry-feeding properties only; studio bookkeeping, labels, visibility and session-dependent properties are excluded; floats are quantized to 1e-9; a Body reached through links contributes only its Placement unless it is one of the operation's own private Bodies), plus the engine stamp and `checker:1`. A verdict is stored once per key in a controller-wide store (4096 entries, shared by documents, preview clones and batches) and persisted compactly in the hidden `KurtShapeProject.KurtShapeResultChecks` property, which `open` and `adopt` create when it is missing (Modified preserved) and read without writing. Keys survive rebuild, undo, rename, save and reopen. A verdict is reused with no kernel work while the native shapes are untouched; when they were recomputed, a copy-free vertex fingerprint of the tool Body and the recorded output tips confirms the kernel reproduced the same result, otherwise the operation is checked again. Measurements (volumes, tight boxes) come from the geometry cache, so unchanged tools, snapshots and results are not re-measured across validations (the spec's substitution of a snapshot by its upstream result is not implemented; a snapshot is measured once per version).

**Modes.** One helper, `Controller._validate_results(doc, mode, …)`, runs for every path that can change a result:

| Path | Mode | Behaviour |
|---|---|---|
| `edit_extrusion`, `set_parameter`, `set_expression` (direct or through an expression), sketch commands outside a lease, `edit_dress_up`, `delete_feature(s)`, `move_face`, `hole`, patterns, `rename_feature`, `set_part_appearance`, every other typed modeling op | `edit` | Inside the request's transaction, after the native gate (`edit_extrusion` additionally keeps its 3.1 own-tip pre-check of the edited operation). Affected operations (key changed or new) are checked; a failed affected operation whose previous verdict was not `failed` rejects and the transaction aborts. Unaffected operations cost a dictionary lookup (`rename_feature`: 0 checks, 0 fingerprints). An operation with an automatic merge scope whose tool stops touching its part is refused earlier by the 3.1 `auto_merge_scope_changed` native gate (`build_failed`) |
| `finish_sketch_edit` | `edit` against the table captured at `begin_sketch_edit` | Read-only (no unrefined retry, nothing persisted); a rejection keeps the lease and the draft (`active_sketch_edit` stays set). After the commit a `report` pass stamps and persists |
| `finish_sketch_edit cancel`, `undo`, `redo` | `report` | No kernel checks; operations whose verdict cannot be reused become `pending` |
| `rollback` | `navigate` | Checks newly active operations without a reusable verdict; **never rejects** (roll-forward exposes failures) |
| `rebuild` | `rebuild` | Validates every pending operation; never rejects |
| `preview` | `preview` | Edit rules in the disposable clone against the source table; `valid` means the commit would be accepted (pre-existing failures fold into `build_status` but do not reject) |
| `check_geometry`, GUI Check Geometry | `check` | Validates pending operations first, read-only; during a lease it reports `pending` with `reason:"sketch_edit_active"` and persists nothing |
| `export`, GUI STEP export | `export` | Validates pending operations first; a failure makes `BuildStatus` `failed` and the existing gate refuses with `build_failed` and `features` (native rows plus result rows) |
| native edits outside managed operations (property editor, console, Sketcher) | — | No checks. The table goes stale: inspect reports `pending` with `reason:"native_change"`, or `failed` with the last-known rows marked `stale:true`. Label, visibility and colour changes never stale it |
| `inspect`, `list_documents`, live GUI previews (`ExtrusionEvaluator`) | — | Never check. Inspect reads an O(1) stamped summary |

**Rejections.** The codes are exactly the creation codes: `empty_add`, `empty_cut`, `invalid_geometry` (with `check`), `build_failed`. The error adds `feature` (the failing operation, which may be downstream of the edited one), `validation:"history"`, `trigger:{op, feature}` (the request's `feature`, `profile`, `sketch` or id; the leased sketch for finish; null for rebuild and rollback), `previous_status` (`valid`, `pending`, `failed` or `new`) and the creation details (`parts`, `tool_volume_mm3`, `check`, `part`, `issues`). The message starts with `Change not applied:`. The document, history, keys and verdict table are unchanged; `last_failed_attempt` records the request. A failed affected operation whose previous verdict was already `failed` never rejects, so recovery can happen in several steps. Example (Kurt's 20x20x10 block with a 20x20 Add of 15 mm and a blind 3 mm Remove on a plane at z = 15; the Add edited to 5 mm):

```json
{"ok": false, "error": {"code": "empty_add", "message": "Change not applied: Raise added no material to part Body",
 "feature": "Raise", "validation": "history", "trigger": {"op": "edit_extrusion", "feature": "Raise"},
 "previous_status": "valid", "parts": [{"part": "Body", "body": "RaisePart", "volume_before_mm3": 4000.0, "volume_after_mm3": 4000.0, "volume_delta_mm3": 0.0}],
 "tool_volume_mm3": 2000.0, "refine": {"requested": true, "retried_unrefined": true, "refined_failure": {"code": "empty_add"}, "hint": "…"}}}
```

**Unrefined retry.** As at creation, a refined result that fails with `build_failed`, `invalid_geometry`, `empty_cut` or `empty_add` is retried once unrefined (exact Boolean first, native automatic fuzz only where exact fails), but only inside a transaction the request will commit or abort (a typed edit, a preview clone, a batch) and at most once per request; a second operation needing a retry rejects with `refine.hint`. The report row carries `refine:{requested, applied, retried_unrefined, refined_failure?}`; undo restores the refined state. `finish_sketch_edit` never retries (an ungrouped lease's native transaction is already committed when it validates; a regrouped lease validates inside its pending grouped transaction, which a rejection aborts: slice A/B U6).

**Responses.** Every accepted mutation of a document with result operations carries `result_check_report:{mode, status, checked:[{feature, operation, status, affected, volume_delta_mm3 | code, message, check, part, check_ms, refine}], reused, fingerprinted, pending:[{feature, reason}], failed:[{feature, code, check, part, message, stale, source:"result_check"}], retry?, keys_ms, ms}`; `check_geometry` and `undo`/`redo` carry it too. `inspect` and `list_documents` add `result_checks:{status:"valid"|"pending"|"failed"|"not_applicable", operations, pending:[ids], failed:[rows], reason?:"native_change"|"sketch_edit_active"|"not_validated"|"native_pending", checker}`, `features[].result_check` (`valid`, `pending` or `failed`, only on result operations), `bodies[].result_check` (the worst status of the part's active result operations) and `bodies[].geometry_state` (`current`, or `retained` when the native geometry predates the intent: Touched/Invalid/Error or a `RebuildReason`). A result failure is current geometry that failed its post-conditions, never retained geometry. `build_status` is `failed` while an active result operation has a failed verdict (or a last-known failure while the table is stale) and such rows appear in `build_errors` with `source:"result_check"`; pending checks never change `build_status` (consistent with 3.0, where `valid` does not imply BRepCheck). Compact rows carry the same `result_check`/`geometry_state` fields. Export sidecars and STEP provenance add `result_checks:{status, operations, checker}`. The GUI status line reads "Result check failed — see Messages" (the rows are appended to Messages) or appends " · checks pending"; Check Geometry and STEP export show a wait cursor while pending operations are validated before the usual worker runs.

**Costs** (FreeCAD 1.1.4 / OCCT 7.8.1, spec probes): key table warm 0.5–8 ms on real files, cold 3.5–44 ms; vertex fingerprint 0.8–18 ms per operation; a full own-position validation 33 ms (mallet) to 5.4 s (28-pocket plate; BRepCheck is 88 % there, tight boxes 63–79 % on curved models). Only affected operations without a reusable verdict are checked; inspect, rename and appearance edits never touch the kernel. Survey of Kurt's seven studio project files (25 result operations): no existing operation fails, so no existing project is refused export. `bench_core` reports `result_validation_ms` and `result_keys_ms` apart from `overhead_ms`; the interaction probe counts `history_checks_by_family` and `fingerprints_by_family`.

**Limitations.** See §3.2.7: dress-up and hole plausibility checks stay creation-time; a native Boolean that fails after an edit is refused by the native gate without the automatic-fuzz fallback creation uses; a closure crossing documents is unkeyable and checked only in `check`/`export`; shape-typed properties of non-parametric objects and parameter stores outside `native_intent` are not part of the key (the fingerprint guards recomputed shapes; a test-only audit mode `KURTSHAPE_RESULT_CHECK_AUDIT=1` rechecks every reused verdict).

### 3.2.2 Model images

U4. `render_view` draws orthographic PNG images of the current parts: standard and custom views, sections, labelled highlights and status banners. It is a **view operation** (`VIEW_OPS`, listed in `non_mutating_operations` but not in `read_operations`): it never changes the document, its undo history, its Modified flag or `LastFailure` (like `inspect`, it first syncs native edits made outside the bridge, which can rotate the revision), and it is allowed on unmanaged documents. Through the bridge it is ledger-tracked like a mutation (`request_id` required), so a render that outlives the 30 s HTTP wait is reconciled with `request_status`. `capabilities.render` publishes the limits below; `diagnostics.renders` reports the service (`{active:false}` until the first render).

```json
{"op": "render_view", "document_id": "<id>", "request_id": "agent-0007",
 "views": ["iso"], "size": [1024, 768],
 "highlights": [{"selector": {"kind": "created_by", "feature": "Pad", "entity_type": "face", "cap": "end"}, "label": "A", "note": "top face"}]}
```

**Request.** Every field is optional (`operation_schema` lists types and defaults).

| Field | Values | Default | Rules |
|---|---|---|---|
| `views` | `iso`, `front`, `back`, `right`, `left`, `top`, `bottom`, `section`, or `{direction:[x,y,z], up?:[x,y,z], name?}` | `["section"]` with a section, else `["iso"]` | 1–7 distinct views; `section` needs `section`; a custom direction and up are nonzero and not parallel (`|cos| < 0.999`); names have 1–24 printable characters |
| `layout` | `separate` (one PNG per view), `sheet` (one PNG tiling 2–7 views) | `separate` | a sheet has 2 columns up to 4 views, else 3 |
| `size` | `[width, height]` px | `[1024, 768]`; a sheet of 5–7 views `[1536, 1152]` | 128–2048 per side, at most 3 145 728 pixels; sheet tiles at least 320 × 240 |
| `parts` | `all`, `visible`, or a list of part, result or sketch ids | `all` | `visible` reads `KurtShapePartVisible`, else the object's `Visibility` (reported as `visibility_source`); an unknown id rejects with `missing_part` |
| `frame` | `included`, `model`, `highlights`, `{center_mm, width_mm}` | `included` | `highlights` needs at least one highlight match in the shown geometry, on the kept side of a section (`highlight_not_rendered`) |
| `highlights` | up to 8 of `{selector \| input, label?, note?}` | none | `selector` is any `resolve_selector` query (also the literal `{feature, subelement}`); `input:{feature, name}` names a stored reference input (`QueryInputs` key, or `helper.input` of an owned helper) and highlights the elements it currently binds natively; labels default to A, B, … and are 1–12 printable characters, unique, without outer spaces; notes up to 48 printable characters |
| `labels`, `part_labels`, `edges` | booleans | `true`, `false`, `true` | highlight labels and legend; short part tags; BREP feature edges |
| `sketches` | `auto`, `none`, `include` | `auto` | `auto` draws the included active sketches only when no included part has faces (sketch-only models render their wires) |
| `section` | `{origin, normal}`, `{plane: XY\|XZ\|YZ, offset}`, `{datum}` | none | see below |
| `quality` | `standard`, `draft` | `standard` | standard supersamples 2× up to 1.1 MP; draft renders 1× with a doubled tolerance |

`expected_revision` is optional; when given it must equal the current revision (`stale_revision`). `measure` is accepted and ignored.

**Views and sections.** All cameras are orthographic. Front looks along +Y (+X right, +Z up), back along −Y, right along −X, left along +X, top along −Z (+Y up), bottom along +Z (−Y up); iso looks along (−1, 1, −1) and shows the +X, −Y and +Z faces. Named section planes use FreeCAD's origin-plane normals, **XY +Z, XZ −Y, YZ +X**, and `offset` is measured along that normal exactly as `create_plane` does (XZ offset 5 is the plane y = −5); `datum` uses the datum plane's world placement. The material on the **+normal side is removed in every view of the request**; the `section` view looks along −normal (from the removed side) with up +Z (+Y when the normal is parallel to Z). Each solid gets its own hatched cap; where two caps overlap they are cross-hatched and listed in `overlapping_parts`. A plane with the drawn parts' whole box on one side rejects with `section_misses_parts` before anything is captured.

A sheet has one image whose `tiles` hold `{view, box_px, camera, highlights}` (cameras offset into the sheet). Each `camera.pixel_from_world` maps homogeneous world millimetres to output pixels ((0, 0) is the top-left corner). PNGs carry tEXt `KurtShape-document`, `revision`, `view`, `render_id` and `note`. A response that includes a part nested in a placed container (not an assembly occurrence) adds `frame_note`: images use the selector world frame, while `inspect`'s `bbox_mm` is container-local for nested Bodies (pre-existing; also in STEP export).

**Honesty rules.** Images show tessellated display meshes; they never establish geometric validity, and every image's caption says so ("display mesh, not a validity check"). Status comes from the same reads as `inspect` (no BRepCheck and no result check is run for a render):

- `geometry` is `retained` when the native build failed or needs a rebuild (the parts keep their last recompute), `current` otherwise, `mixed` when per-part states differ. A result-check failure is current geometry that failed its post-conditions.
- Banners, in this order: `RETAINED GEOMETRY · BUILD FAILED` (native failure), `RETAINED GEOMETRY · NEEDS REBUILD`, `VALIDATION FAILED` / `VALIDATION PENDING` (result checks, §3.2.1), `BREPCHECK INVALID` (a cached `check_geometry` verdict), `NOT A SOLID: n PART(S)` (non-solid results are drawn two-sided and get no caps), `ROLLED BACK k/n`, `UNMANAGED FILE`.
- Highlight matches are classified: in the shown geometry (`rendered:true`), or `reason` `sketch` (a sketch that is not drawn), `filtered_part` (a part excluded by `parts`) or `history` (a consumed or earlier feature, e.g. a fillet's input edge). Non-rendered matches are drawn as dashed ghosts, add only `ghost_px`, and never count as `visible` or for framing. An occluded highlight gets a hollow "X (hidden)" label, never a solid one.
- `stale` is true when the document changed (revision, generation, change serial, or an unsynced native edit) between capture and completion: the image still depicts `revision`; call `inspect`.

**Execution.** The owner thread validates the request, syncs the document (as `inspect` does), keys the image and either answers from the cache (`cached:true`, synchronous) or captures detached world BREPs of the drawn parts and the highlight elements, writes the scene and starts one private render child. Captures are reused across settings-only changes (views, size, section, highlights, labels), and so are resolved highlights and their exported elements (keyed by the capture and each highlight's selector or input; labels and notes do not count); a model edit or a new revision captures and resolves again. Highlights matching the same elements share one exported file. Every response field describes the captured scene: part names, colours and status are frozen at capture, never read from the live document when the job completes. Through the bridge the job completes from the GUI tick (the request is parked, other requests are served meanwhile); a direct `Controller.dispatch` waits for it. One render runs at a time: an identical request joins it, a different one gets `render_busy` with `retry_after_ms`.

The renderer (N2): each part is meshed once per job by OCCT with a linear tolerance of 0.6 × the finest mm/px (rounded down to a power of two, clamped to 1e-4–2e-3 × the scene diagonal, doubled for draft) and an angular deflection of 0.25 rad. Above 1.5 M triangles the mesh is coarsened (tolerance and angle doubled, the angle up to 0.5 rad) at most three times, stopping when a step removes less than 10 %; above 2.5 M triangles, section caps and highlight faces included, or past the job's 18 s budget, the render is refused with `render_too_large`. A face several highlights match is drawn in the colour of the highlight with fewer faces. Images narrower than 320 px shorten the banners ("RETAINED · FAILED") and drop the scale bar and axis triad before the caption.

The worker (N3): each render runs in a private one-shot child process (below normal priority, single-thread BLAS, 1536 MiB commit cap in a Windows Job Object, 25 s limit) that is killed when KurtShape exits. Its inputs are BREP captures checked against their sha256 before any native module loads, and every PNG is checked again (type, size, sha256) before it is published.

**Limits.** Prescreen (owner, before any export): at most 5000 faces and 20000 edges over the drawn parts, then a running 48 MiB BREP cap (`render_too_large` with `reason` `faces`, `edges` or `brep_bytes`). Highlights: 256 matches per item, 1024 in total (`too_many_highlight_matches`).

**Retry, cache and artifacts.** On a bridge `timeout`/`outcome_unknown`, look the `request_id` up with `request_status` (`started`: poll with backoff; `completed`/`failed`: the stored response). Because a render cannot change the model, `not_recorded`, `expired` or a restarted session may be settled by sending a new request with a new `request_id`: identical settings return a cache hit, a remembered failure, or join the running job. Images live in `<session>/renders/<session_id>/` (session-private, one folder per controller, deleted when KurtShape closes; folders of owners that provably exited are swept); the cache holds 64 entries (images and remembered failures) or 96 MiB of images (LRU). Deterministic failures (`render_too_large` from the inputs, renderer failures) are remembered for 10 minutes under the same key and returned with `cached:true`; timeouts, cancellations, transient OS errors and an overrun of the 18 s budget are not.

`render_view` is not previewable, not batchable and never part of `preview`.

The second view operation, `set_view` (2026-10-20), aims the app's own 3D view with the same view directions; see [Viewport camera](#viewport-camera-set_view-gui-2026-10-20).

### 3.2.3 Parameters

U5 (backend; the parameters panel is U7). A document's model parameters live in one native `App::VarSet` at the top level, Name and Label `Params` (`Params001` if the name is taken), marked by a hidden `KurtShapeParameterSet`. FreeCAD expressions are the only evaluator and the FCStd holds the only copy of values and formulas; documents without parameters are unchanged. Scope is the whole document (all parts); parameters sit outside history, so rollback, splits, booleans and part deletions never move them.

**Types and units.** `length` (App::PropertyDistance, mm, may be negative), `angle` (App::PropertyAngle, radians on the wire, stored in exact degrees: `"15 deg"` and 0.2617993877991494 rad both store 15.0; |deg| ≤ 360 for values and formulas) and `number` (unitless float). A value is a number in wire units or a quantity string; send angle edits as `"<n> deg"`. Natively added `App::PropertyLength` reads as `length`; other native types read as `unsupported` (listable, renamable, deletable, not editable).

**Names.** A name starts with a lowercase letter (`^[a-z][A-Za-z0-9_]{0,63}$`, e.g. `shaft_diameter`), is unique case-insensitively, does not start with `kurtshape`, is not an attribute of the set (`touch`, `isValid`, …) and is free in the expression language (not a unit such as `mm`, `t`, `h`; not a constant `pi`, `e`; not a function `sin`, `count`): `invalid_parameter_name` with `reason` `format`, `reserved`, `reserved_attribute`, `unit`, `constant`, `function` or `expression_token`; `duplicate_parameter` with `existing`. The feature id `Params` is reserved (`invalid_argument`, `reason:"reserved_id"`).

**Formulas.** One validator serves every formula path (`set_expression`, `edit_extrusion`, `edit_dress_up`, Hole formulas, `bind` and parameter formulas): at most 512 characters of `A-Z a-z 0-9 _ . , + - * / ^ ( ) [ ]` and spaces; no `_`-prefixed pseudo-objects; evaluated natively in the target's context before anything changes; the unit must match the target (lengths accept a length or a unitless value read as mm; angles need an angle; numbers need a unitless value), else `unit_mismatch {expected_unit, actual_unit, expression, hint}`; cycles reject with `expression_cycle`. Bare parameter names in consumer formulas are stored qualified (`shaft_diameter` → `Params.shaft_diameter`); a label-qualified reference after a native relabel rejects with `reason:"label_reference"`. A parameter's own formula reads only parameters (`reason:"reads <name>"`).

**Operations** (none takes `body`; the four mutations are model operations: one undo step, `expected_revision`, previewable; `create_parameter` and `edit_parameter` are batchable, rename and delete are not):

| Operation | Arguments | Effect |
|---|---|---|
| `list_parameters` (read, also on unmanaged files) | `names` (optional, 1–256) | `{parameter_set, other_parameter_sets, warnings, parameters:[row]}`; rows add `depends_on`, `used_by_parameters`, `used_by:[{feature, native_feature, parameter, path, expression}]` and `affects:{features, parts}`; warnings report `dangling_reference` (a formula naming no parameter) and `extra_parameter_set` |
| `create_parameter` | `name`, `type`, `value` or `expression`, `bind:[{feature, parameter}]` (≤ 64) | `type` is inferred from bind targets, a quantity string or the formula's unit (plain numbers need it). Bind targets are inspect `native_parameters` rows: driving, not formula-driven (`expression_driven`) and of the parameter's unit; without a value or formula they must agree (`bind_values_differ {targets}`) and give the value. One managed rebuild for any number of binds. Returns `created_parameter` and `parameter_report {row, bound, changed_inputs, rebound, pruned}` |
| `edit_parameter` | `name`, `value` and/or `expression` (`null` clears and keeps the value) | A value on a formula-driven parameter rejects with `expression_driven`. Returns `parameter_report {previous, current, changed_parameters, changed_inputs, affected:{features, parts}, pruned}` |
| `rename_parameter` | `name`, `new_name` | Native rename rewrites every consumer; any consumer whose value would change or break rejects with `rename_failed {broken}`; dangling consumers that name `new_name` are re-bound and reported |
| `delete_parameter` | `name`, `freeze_consumers` (false) | With consumers: `parameter_in_use {consumers, hint}` unless `freeze_consumers`, which clears their formulas (values kept) and reports them as `frozen` |

**Rows** (`inspect.parameters` compact, `list_parameters` full): `name, type, unit, value, native_value, native_unit, expression, expression_ref` (`Params.<name>`), `native_type, status` (`valid`, `needs_rebuild` when the set is touched, `invalid` with `error` when its formula fails), `used_by_count`. `inspect` adds `parameter_set:{id, label, state, error}` (null without parameters) and, when present, `other_parameter_sets` (unmarked VarSets and extra marked sets, read-only; the first marked set is authoritative). No VarSet is ever a `features` row. A touched set makes the document and every `bodies[]` row `needs_rebuild`; an invalid set fails them. Compact feature rows gain `uses_parameters` (parameter names their formulas read) when there are any.

**Bindable targets** (the `native_parameters` rows): sketch driving Distance, DistanceX, DistanceY, Diameter, Radius (mm) and Angle (rad); legacy Pad/blind Pocket Length; studio Extrude Length; Revolution Angle; Plane Offset (and a line-angle plane's Angle); Helix Pitch, Height, Radius; Fillet Radius; Chamfer Size; Thickness; Hole Diameter, Depth (blind), PointAngle (angled blind). Pattern counts and spacing, transforms, sweep, loft and move-face values reject with `unsupported_parameter`.

**After every formula change** (`verify_applied`, after the step's recompute and native gate): each changed native value took its formula's value (`parameter_not_applied {feature, parameter, expected, actual}`), helices stay within 1000 turns and segments (checked before the rebuild too), and Holes re-run their own checks (a formula that drives Diameter and Depth together is not mistaken for a native rewrite; a depth beyond the native maximum rejects with `invalid_argument`, `maximum_depth`). There is no sign rule: signed formulas stay signed. Result checks (§3.2.1) then validate the affected Add/Remove/Intersect operations; their keys follow the values a parameter produces, so a rename, a freeze or a no-op edit re-checks nothing.

**Pruning.** FreeCAD dependencies are object level, so a parameter edit would rebuild every consumer of the set. Consumers whose evaluated inputs did not change (and that were not already touched) are not rebuilt (`parameter_report.pruned`); preview prunes exactly as the commit. `KURTSHAPE_FULL_PARAMETER_RECOMPUTE=1` turns pruning off.

**Errors and rollback.** Any failure rolls the request back; `error.parameter = {name, operation, accepted:{value, native_value, expression}}` gives the parameter as it stands afterwards (for example `edit_parameter shaft_diameter 0` → `build_failed`, `accepted.value` 8). Native edits made outside managed operations (property editor, console) follow §3.2.1: affected results read `pending` and export validates first; a silent native rename re-keys the document. A name that hides a type attribute of the set (only possible natively) makes every operation reject with `invalid_parameter_set {names}` until it is renamed in the property editor.

`capabilities.parameters`: `{scope:"document", set_id:"Params", types:{length:"mm", angle:"rad", number:""}, native_units:{angle:"deg"}, name_pattern, operations, batchable:["create_parameter","edit_parameter"], bindable, pruning}`.

**In the app (U7).** The left panel's Parameters section (between Features and Parts) uses the same operations through the panel: typing never dispatches, Enter (or a focus move inside the window) commits one `edit_parameter` = one undo step, and a window switch leaves a visible pending edit. GUI angles are typed in degrees; `=` starts a formula; Esc discards. Copy reference puts the backend's `expression_ref` on the clipboard for a feature's Formula field; agents bind with that returned string too, never a hard-coded `Params.x`. The parameter set is never a history row.

### 3.2.4 Atomic batches and preview `accepted`

Owner U6 (`src/kurtshape/batch.py`, spec `runtime/contract-3.2/specs/batch.md`). `accepted` itself is defined in §3.2.0 and shipped by U1.

**`batch`** (`{"op":"batch", document_id, expected_revision, request_id, "label":"boss with round", "measure":true, "steps":[…]}`, mutation, ledger-tracked) runs 1–32 modeling steps inside **one** native transaction. A step is a modeling request without envelope fields (`document_id`, `expected_revision`, `request_id`, `measure` reject with `unknown_argument`, `transport`), plus an optional alias `as` (a letter, then up to 31 letters, digits or underscores, unique in the batch). `{"$ref":"a"}` anywhere in a later step stands for step `a`'s created feature, `{"$part":"a"}` for its single output part (fields such as `profile`, `support`, `sketch`, `part`, `parts`, `merge_scope`, `body`, a selector's `query.part`); only whole values are substituted, so feature ids inside formula strings must be explicit `id`s. `label` (1–80 printable characters) names the undo step `KurtShape: batch <label>`, otherwise `KurtShape: batch (<n> steps)`.

Batchable operations are `MODEL_OPS` minus `capabilities.batch.excluded` (with reasons): `rebuild`, `rollback`, `delete_feature`, `delete_features`, `repair_orphan_helpers`, `duplicate_feature`, `rename_parameter` and `delete_parameter`; everything outside `MODEL_OPS` (reads, `render_view`, lifecycle, history, assembly, `batch` itself) is excluded automatically.

**Acceptance.** Each step runs through the single-operation gates (`_model_step`: handler, studio reconciliation, recompute, native build gate, applied-formula check, legacy one-solid gate); the result checks of §3.2.1 then run once over the whole batch before the commit, so a step that empties a downstream result and a later step that repairs it are accepted together. On success the response is the usual inspection plus `batch_report:{label, transaction, base_revision, step_count, completed_steps, created_features, steps:[{index, op, as, created_feature, features, parts, ms, result_report?, parameter_report?, …}], validation}`; the revision rotates once and native history gains one entry. There is no top-level `created_feature` for a batch.

**Failure changes nothing** (revision, undo names, objects, geometry, parameters); a rejection after the first change clears the native redo list, as any rejected mutation does. The error keeps the step's own `code` and details, its message gains the prefix `Step i (op): `, and `batch:{step, op, as, phase, steps_completed, step_count, rolled_back, step_request}` names the step (`phase:"step"`) or, for a final result-check failure, the last step that changed the failing feature (`phase:"final_validation"`, `step` null when it cannot be attributed). `step_request` (the step after reference resolution) appears in the response and the ledger only; the document's `LastFailure` holds a compact record `{request:{op:"batch", request_id, label, step_count}, error:{code, message, feature?, batch}, rejected}` of at most 2 KiB. Before any change: `unmanaged_transaction` (a pending native transaction), `invalid_argument` (steps not a list of 1–32 objects, a bad `label` or `as`, a malformed reference, nesting deeper than 64, duplicate literal `id`s, a step missing a required field), `request_too_large` (the canonical steps JSON exceeds 65,536 bytes), `unknown_argument`, `unsupported_operation` (with `reason`) and `invalid_step_reference` (an unknown, forward or self alias, `$ref` to a step that creates no feature, `$part` to one that creates no part). At run time: any step code, `invalid_step_reference` (the referenced step produced no feature, or not exactly one part: `parts`), the result-check codes, `batch_time_budget_exceeded` and `transaction_split`.

**Time budget.** In the app a batch stops before its next step (or before its result checks) once two thirds of the bridge timeout have passed: `batch_time_budget_exceeded {steps_completed, elapsed_ms, budget_ms}`, rolled back, so the GUI answers with a clean failure instead of `outcome_unknown`. A single long step is not interrupted. Headless controllers have no budget unless `request_budget_s` is set. Practical limit: in the app a step costs what its recompute and display update cost, which grows with the model (U10, 2026-10-19: a 20-step chunk of `sketch_circle` + `pocket` on a 300 mm studio plate took 9.6 s with no holes yet, while with 10–20 holes only 17–18 steps fit in 20 s, about 1.1 s per step), so the 32-step maximum fits only light steps. On a large part keep batches to about 12 steps and preview first.

**Transaction splits.** A step that commits or opens a native transaction of its own breaks the batch; the commit counter and the active-transaction check find it, the batch undoes what was committed, writes a `KurtShape: discarded failed batch` history entry (managed `undo`/`redo` step over it, like a cancelled sketch edit) and rotates the revision: `transaction_split {rolled_back, revision_rotated:true, residual_objects?, cause?}`. `rolled_back:false` (with `residual_objects:{added, removed}`) means a change made outside any transaction could not be undone: inspect before continuing. No KurtShape handler does this; a static test keeps the list of transaction callers reviewed.

**Ledger.** One record per batch: an identical replay returns the stored success or failure without running anything, another payload under the same `request_id` gives `request_id_reused`, and a bridge timeout is reconciled with `request_status` as for any mutation. After a restart (`not_recorded`) the old `expected_revision` is stale, so a resend cannot run twice; inspect and reconcile by explicit `id`s.

**Preview.** `{"op":"preview", …, "proposal":{"op":"batch", "steps":[…], "label":…}}` runs the same steps and the same final checks on a disposable clone. Proposal keys other than `op`, `steps`, `label` give `unknown_argument`; a pending native transaction gives `unmanaged_transaction` (a single-op preview keeps `sketch_edit_active`); structural errors (validation, unknown proposal keys) come back without a clone as `{ok:true, result:{accepted:false, valid:false, error:<the commit's error>, build_status:null, measurements:null, batch_report:{completed_steps:0, steps:[]}}}`. The result is `{base_revision, proposal:{op:"batch", label, step_count}, accepted, valid, error, build_status, build_errors, measurements, discarded:true, batch_report:{step_count, completed_steps, steps, validation}}`; on failure `error` is the object the commit would return (with `batch.*`) and `measurements` is null. `accepted` is true exactly when the commit would return `ok:true`. Commit with the same steps, `expected_revision = base_revision` and a new `request_id`. A preview is untracked: after a bridge timeout re-run it, smaller. Examples: `examples/batch-request.json`, `examples/preview-batch-request.json`.

`capabilities.batch`: `{operation:"batch", operations, excluded, max_steps:32, references, undo:"one native undo step", preview, validation}`; `preview_operations` includes `batch`.

### 3.2.5 Identity, schemas, lifecycle, compact inspect, transport, client

*Identity, schemas, missing fields (U2a), lifecycle (U2b), compact inspection (U2c), transport (U2d) and the client (U8) are in place.*

**Client reconciliation** (`tools/assistant_client.py`, stdlib). `send(request, session_path=None, *, wait=300, reconcile=True, resend=True)` reads the session file once, gives every non-read operation a `request_id` (kept for life: a mutation is never re-sent under a new id), refuses a body over 65,536 bytes locally (`request_too_large`, nothing sent) and never raises for transport errors. `wait` is one budget for the whole call; the first POST gets at least half of a short budget (up to 2 s) and leaves room for a status poll, so a `wait` under about 5 s means "send, then reconcile": an operation slower than half the budget ends `pending` and is settled later with the same `request_id`. A clean answer is returned unchanged; a rejection (`invalid_request`, `stale_revision`, `request_id_reused`, …) is returned unchanged without polling. When the bridge cannot say whether a mutation ran (`outcome_unknown`, `request_pending`, a timeout, a reset, a non-JSON 5xx) the client polls `{"op":"request_status","request_id":…}` (the bridge answers it without the owner queue) at the URL and token it started with, backing off from 0.25 s to 2 s, and adds `reconciliation:{outcome, status?, request_id, session_id, polls, resent, waited_s, reason?, retry_safe?}`: `completed`/`failed` return the stored response; `not_executed` only when the request provably never started (`timeout` in the queue, `queue_full`, ledger `cancelled`, or a refused first connect); `pending` (`outcome_pending`) when it was still queued or started at the deadline; `unknown` otherwise (`expired`, `request_expired`, `session_changed`, `session_ended` after a 403, `unreachable` after 5 s of refused polls, `not_recorded`, `deadline`). A request `not_recorded` for 1 s in the same session is re-sent once, byte-identical (and the resend's own definitive answer is returned). A read that fails in transport, and an unknown outcome of a non-mutating view operation (`render_view`), carry `retry_safe:true`. CLI: `--json`, `--request-file`, `--session` as before, plus `--request-id ID` (an identical rerun replays through the ledger), `--wait S` (default 75 s), `--no-reconcile`, `--status ID`, `--reconcile --request-id ID` (with `--json`/`--request-file` and `--session-id`, the session printed on stderr when the request was first sent, it may re-send the identical body once, but only into that same session; another session gives `unknown`, `session_changed`) and `--build-check` (`{verdict: current|stale|different_tree|unknown, running, checkout}` against this checkout's `src/kurtshape`). Exit codes by the next action: 0 ok or completed, 1 rejected or failed, 2 pending (reconcile later with the same id), 3 unknown (inspect before acting), 4 safe to retry (inspect first; a mutation needs a new `request_id`, because the ledger replays the old answer), 64 usage error (nothing sent); a missing session file is 4 for requests; `--build-check` exits 0 only for `current`. `tools/assistant.ps1` throws a message per code.

**Loaded build identity.** `capabilities.build` reports what the running process loaded: `{id, source_sha256, source_files, source_dir, loaded_at, pid, python, workers_load_from_disk, git, on_disk}`. `source_sha256` is SHA-256 over `<name>\0<sha256 of the LF-normalised file>\n` for every `*.py` directly in the package, in name order, taken once at the first `kurtshape` import; `id` is `src-` plus its first 16 hex digits, so CRLF and LF checkouts of the same sources match. `git` always carries `state`, `head`, `ref` (at load), `head_now` and `head_moved`; `state` is `pending` until the one background comparison of the process (started by the bridge or the first `identity()` call, never at import) finishes, then `ready` with `dirty`, `modified`, `untracked` and `deleted` against the commit checked out at load, or `unavailable` with a `reason` (not a checkout, SHA-256 repository, git missing or killed after 10 s). `on_disk` (`matches_loaded`, `changed`, `added`, `removed`) stats the package on every call; modules `core` imports lazily are read from disk at first use, so `matches_loaded:false` means restart to be sure. `diagnostics.build` is the same block. The session file carries `build: {id, source_sha256, source_dir, loaded_at, git_head}`; export sidecars and STEP provenance carry `kurtshape_build: {id, source_sha256, git_head}`, constant for the life of the process. Worker processes (`KURTSHAPE_WORKER=1`) capture nothing. `python -B -m kurtshape.build_identity <checkout>\src\kurtshape` prints the digest of a tree; same directory and digest means the app runs your code, same directory and another digest means it predates your edits (ask Kurt before restarting), another directory means another tree (for example KurtShape-green). Test reports from `tools/run_native_tests.py` record `kurtshape_build_sha256` for the same comparison.

**Operation schemas.** `operation_schema` (read, documentless, never ledgered; optional `operations:[name,…]`, distinct strings, omitted or `null` means all) returns `{schema_version:1, contract, contract_revision, digest, $defs, x-example-fixtures, x-example-placeholders, operations:{op:{kind, summary, undoable, preview, batch, request, requires_one_of, checked_by_handler, x-required-when, constraints, examples, x-example-fixture, doc}}}` (the two `x-example-*` maps describe the fixtures the examples run on). A non-list, duplicate or unknown name rejects with `invalid_argument` (`fields:["operations"]`, plus `unknown:[…]`). `request` is a JSON schema of the whole request: the envelope (`op`, `document_id`, `expected_revision`, `request_id`, `measure`) with `x-ignored` where an op ignores a field and `x-bridge-only` on `request_id` for tracked ops, then one property per argument. `required` is truthful: only fields without which the request is meaningless; `checked_by_handler` lists required fields whose absence the handler reports with its own code; `x-required-when` documents mode-dependent fields; defaults live only in the per-op fields (`x-default-when` says when a mode-dependent default applies); enums come from the owning module's constants. `capabilities.schemas` is `{operation:"operation_schema", schema_version, digest, operation_count}`; `digest` is the SHA-256 of the canonical JSON (sorted keys, compact separators) of the document without `digest`, built once per process, so clients cache by it. `capabilities.read_operations` and `non_mutating_operations` list the classes a client needs for reconciliation (§3.2.0). Example: `examples/operation_schema-request.json`.

**Unsaved changes.** `inspect`, `list_documents` and every successful document response carry `modified`, `modified_basis` and `unsaved`. With a GUI document the basis is `gui` (FreeCAD's Modified flag); headless it is `session`: modified means the revision differs from the one last saved or opened in this session, so `new`, `import_step` and `recover` start modified and unsaved (`unsaved` is `modified or no native file`), every accepted mutation makes the document modified, and `save`, `open` and `adopt` clear both (their responses already say so). Undo back to the saved state stays modified in both bases, as does a script that calls `doc.save()` directly. Reads, `export`, `check_geometry` and rejected requests change neither flag; a rejected request also restores the GUI flag it found when nothing was committed and the content signature is unchanged.

**`close_document`** (`{"op":"close_document", document_id, expected_revision, request_id, "discard":false}`, lifecycle op, not previewable, not batchable, allowed on unmanaged documents). `expected_revision` is required, as for every non-read op: a missing or stale one is refused with `stale_revision` (`expected`, `actual`) before any of the refusals below. Every refusal happens before the native close and leaves the document open: a non-boolean `discard` → `invalid_argument`; a pending native transaction → `unmanaged_transaction`; the GUI editing that document (feature editor, task, placement, a STEP export or geometry check in flight) → `user_editing` with `tool`; objects of other open documents linking into it → `document_in_use` with `users:[{document, object}]`, whatever `discard` says; unsaved changes or a never-saved document without `discard:true` → `unsaved_changes` with `reasons` (`modified`, `never_saved`), `modified_basis`, `native_file`, `revision`; an unmanaged native file with changes → `unsaved_changes` with `discard_unsupported:true` even with `discard` (save or close it in FreeCAD). With `discard:true` a managed document is first checkpointed to `<DocumentId>.discarded-<rev12>.FCStd` + `.json` (`rev12` = the first 12 hex digits of the revision; the manifest carries the full revision) in the session's `project-recovery` folder (`checkpoint_failed` keeps the document open); `recover` accepts that manifest, and only the newest 20 discard pairs are kept. The result is `{closed:{document_id, name, native_file, revision, modified, modified_basis, never_saved, discarded_unsaved_changes, recovery_manifest}, open_documents:[ids], operation_ms}`; a later request for that id gives `unknown_document`, an identical retry replays the result. Save, then close, is two requests: `save` does not rotate the revision. The usual mutation guards apply (`stale_revision`, `busy`, `sketch_edit_active`). `App.closeDocument` shows no dialog; the GUI behaviour is verified by the `document-lifecycle` recipe.

**Compact inspection.** `inspect` with `detail:"compact"`, `features:[id,…]` or `parts:[id,…]` (a selection implies compact and an explicit `null` selection counts as absent; `detail:"full"` with a selection, a bad `detail`, or a non-list or duplicate selection reject with `invalid_argument`; unknown ids reject with `missing_reference` `features:[…]` or `missing_part` `parts:[…]`) returns the status header instead of every feature row: `document_id`, `revision`, `name`, `native_file`, `modified`, `modified_basis`, `unsaved`, `managed`, `build_status`, `rebuild_reason`, `build_errors`, `geometry_check` (the cached verdict), `active_sketch_edit`, `detail:"compact"`, `studio:{enabled, rollback_index, history_count}`. Without a selection the overview adds `history:{ids, rolled_back, rollback_index}` and every part row; `features` adds those feature rows in history order (part rows only when `parts` is also given); `parts` alone adds those part rows plus the rows of the features they own or output. A feature row is `{id, name, type, state, history_index, rolled_back, part, output_parts, parameters, expressions, depends_on, used_by, affects, reference_health}` (plus `reference_consumers` for an operation with hidden helpers): `depends_on` (OutList), `used_by` (InList) and `affects` (every downstream object) name history features in history order, a hidden helper counts as the operation that owns it, and Bodies, origins and metadata are dropped; `parameters`, `expressions` and `reference_health` equal the full row's. A part row is `{id, name, body, tip, visible, color, build_status, geometry_check, features, reference_issues:{count, features}, measurements}`; `measurements` is null unless `measure` is given (then it has the requested level), and nothing is measured or checked otherwise; `reference_issues` counts the unhealthy inputs of the part's features including their hidden helpers' (the same entries the feature rows show), and `used_by`/`affects` never list objects of other documents. `list_documents` with `detail:"compact"` returns one header row per document with `feature_count` and `part_count`. Compact mode runs the same status synchronisation as a full inspection, so its `revision` is the full inspection's; it is timed as `inspection_compact`. Full mode (`detail:"full"` or omitted without a selection) is unchanged. Since 2026-10-22 every mutation takes `detail` as well (compact header, full, or the default without `operations`/`last_failed_attempt`): see the slice A/B U6 subsection at the end of this document.

**Transport.** The bridge keeps its guards in this order: token, path and Origin (403), media type (403), body size (413, `request_size_limit` of the session file), then the body. A body that is not one JSON object, has a bad `Content-Length` or contains a non-finite number answers HTTP 400 with `{"ok":false,"error":{"code":"invalid_request","message":…}}` and registers nothing. A full owner queue answers HTTP 503 with `Retry-After: 1` and `{"code":"queue_full","request_id","session_id"}`; a tracked request is recorded as `cancelled` and was never started; the ledger now replays that answer for the id, so retry it with a new `request_id`. A read that was started and timed out answers `outcome_unknown` with `tracked:false`: it is not in the ledger, `request_status` cannot settle it and resending is safe. The session file lists `build`, `read_operations`, `non_mutating_operations` and `request_size_limit` beside the contract identity. Quiet reads (`QUIET_OPS`: `capabilities`, `operation_schema`, `diagnostics`, `request_status`, `list_documents`, `inspect`, `resolve_selector`, `orphan_helpers`) leave the GUI alone: after one of them (or after a request cancelled in its queue) the panel runs no trailing inspect and no refresh unless the document's revision, build status or refresh flag moved, and it reads only its own managed document for that decision; `check_geometry`, `preview` and `assembly_candidates` still refresh.

**Missing fields.** Before any document lookup, a request missing a generic-required field (absent or `null`) rejects with `invalid_argument`, `fields`, `reason:"missing_required"` and, for an empty `requires_one_of` group, `one_of:true`. A field the handler needs only in one mode surfaces after rollback as `invalid_argument` with `reason:"missing_conditional"`. Envelope requirements are documentation: a missing `expected_revision` still gives `stale_revision`, a missing `request_id` is still allowed headless, `request_status` without an id still answers `not_recorded`, and `set_expression` without `expression` still clears the formula.

### 3.2.7 Known limitations

- Units U2–U9 append theirs here. U1: none.
- U3: dress-up (fillet/chamfer) volume plausibility and hole empty-cut/depth/plausibility are still checked at creation and on their own parameter edits only; patterns, `boolean_parts`, `split_part`, `move_face` and `operation:"new"` have no history checks. An edit after which an exact Boolean fails *natively* is refused by the native gate (`build_failed`) before validation, without the automatic-fuzz fallback creation uses. `finish_sketch_edit` validates read-only and never runs the unrefined retry (an ungrouped lease's native Sketcher transaction is already committed; a regrouped lease's transaction is pending, but no retry runs there either: the grouped-transaction retry of the spec is not implemented). A deletion another result operation consumes is refused by the structural gate (`external_dependency`) before validation, so the validator's cascade hint only applies to deletions that pass it. A closure crossing documents is unkeyable (always `pending`, checked in `check`/`export`). Keys cover what `native_intent` reads: shape-typed properties of non-parametric objects and parameter stores outside it are not keyed (the fingerprint guards recomputed shapes; `KURTSHAPE_RESULT_CHECK_AUDIT=1` rechecks every reused verdict in tests). Headless sessions cannot observe the GUI Modified flag the property creation preserves (the `result-validation` GUI recipe does). The GUI Check Geometry worker refuses its archive on Part Studio documents ("The loaded archive does not match the captured geometry"); this predates 3.2 (reproduced on the frozen 3.1 tree) and the synchronous result validation before the capture still runs and is shown.
- Build identity compares only SHA-1 repositories (a SHA-256 repository reports `unavailable`); modules `core` imports lazily are read from disk at first use, so `on_disk.matches_loaded:false` means restart to be sure; a git that escapes the tree kill is left to finish after the probe reported the timeout (U2a).
- `adopt` leaves FreeCAD's application-level transaction "KurtShape: adopt native copy" open, so the next document opened in that process starts with a pending transaction (pre-existing, recorded by N4).
- The session basis of `modified` is conservative: undo back to the saved state, `begin_sketch_edit` and an out-of-band `doc.save()` all leave it modified. Only `close_document` consults the GUI editor hook; other agent mutations still cancel an open feature editor (F-14). Discard checkpoints cost one FCStd each, capped at 20 per recovery folder (U2b).
- U4 (`render_view`): renders show display meshes in the selector world frame; `inspect`'s `bbox_mm` and STEP export use `assembly.global_shape`, which is container-local for Bodies nested in a placed `App::Part` (pre-existing, flagged by `frame_note`, not fixed in 3.2). Images are session artifacts: they are deleted when KurtShape closes. One render runs at a time. A render has an 18 s budget inside the 25 s child limit; meshing cost is dominated by OCCT on curved BSpline faces and does not fall with coarsening, so scenes near the prescreen caps can run out of time (76 drill copies at 2048×1536 take 16–17 s), and near the limit the outcome depends on machine load. Peak commit stays under 600 MiB except at the prescreen extreme (about 630 MiB); the Job Object's 1536 MiB cap is the hard bound, its memory-limit notification is best-effort, and off Windows there is no hard cap. The silhouette test is slope-aware; faint streaks can remain where steep helical faces meet end-on, and overlaps narrower than about two supersampled pixels are not cross-hatched. Highlights on consumed features are drawn as ghosts at their own (historical) position, not at a rollback position; there is no `at_feature` render. Resolving new highlights runs the selector engine on the GUI thread: a `closest` selector measures the exact distance to each nearby candidate (about 40 ms per query against a face with 60 holes), so eight new closest-point highlights on a 60-hole plate take about 0.3 s of GUI-thread time; repeating them with other views, sizes, sections or labels takes under 0.1 s.
- U5 (parameters): names must start with a lowercase letter (no `OD` or `L1`); usage attribution tokenises formulas (native truth is object level), so exotic natively authored formulas can be misattributed in `used_by` (rename and delete keep native-evaluation safety nets); rename and delete are not batchable; helix turn limits are checked before the rebuild, but a Hole's own checks (and the applied-value check) run after it, so a refused Hole edit has paid one rebuild; natively added parameter types other than distance, length, angle and float are listed as `unsupported`; feature ids that are unit symbols (`C`, `A`, `m`, …) break studio's internal formulas (pre-existing, not changed).
- U6 (batches): deletions, rollback, rename/delete of parameters and `duplicate_feature` are not batchable; a single long step is not interrupted by the time budget, and a batch preview cannot be reconciled after a bridge timeout (re-run it, smaller); FreeCAD's own AutoSaver is not guarded by `busy`, so its crash-recovery file (not Kurt's file or KurtShape checkpoints) could in principle capture a mid-batch state, as it could a long single operation; a transaction split followed by a change outside any transaction cannot be undone and is reported with `rolled_back:false`.

Canonical HTTP status lookup (`{"op":"request_status","request_id":"..."}` with a 1–128-character string ID) reads the shared session ledger without entering the CAD command queue when using the supported Controller and a valid current measurement default. It remains available while the owner is busy or the queue is full, subject to Python GIL scheduling and ledger-lock contention. Authentication, path, Origin, media type, size and JSON-body guards still apply first. The result retains the original request/session IDs and deep-copied response, including its original operation time. Status has no operation time of its own; the wire reports `queue_wait_ms:0.0`. These nonqueued reads do not add owner-thread operation or queue timing samples.

Other request shapes retain the existing queued Controller validation, including optional fields, missing/noncanonical IDs, invalid measurement values/defaults and nonstandard controllers. This optimization adds no request-ID validation rule to `request_status`, registers no status request and does not change ledger capacity, replay or timeout semantics. A status read describes the ledger at the time its lock is held; `not_recorded` still does not prove a command never ran.

Typed modeling and begin-edit requests accept optional `body` except `create_body`/`rebuild`. Inspection adds `managed`, `unsupported_objects` and per-result `bodies`, including standalone Part solids. Aggregate and per-result status/measurements distinguish current and retained geometry. One-solid validation applies to the affected PartDesign Body, not the entire document.

Quantity strings accept units and arithmetic (`1/8 in`, `12.7/2`, `90 deg`). Explicit angles convert FreeCAD's internal degrees into the radian contract. Wrong dimensions, booleans and nonfinite values reject. Document-dependent formulas use `set_expression`; the unbound native input fields stage values until dispatch.

Human save/export dialogs persist destination-folder grants and recent projects in the local profile. New profiles use `workspace_layout:"portable"` and default to `<checkout>/projects` only. Existing settings files without a layout marker retain the legacy roots (the checkout's parent and its grandparent's `projects` folder, historically `CADkz/Codex` and `CADkz/projects`); this choice persists on the next settings save. Explicit destination grants remain additive in either layout. The bridge cannot grant itself another folder. Unmanaged FCStd opens with a transient session identity and no added input metadata. Typed/native app modeling is guarded until adoption. Adoption rejects script/proxy objects and cross-document dependencies; it does not certify every native object for every typed operation.

STEP import reads with FreeCAD Part/OCCT, validates before publishing a new native document, preserves occurrences/placements without fusing solids, and stores an `ImportSource` provenance property. Inspection exposes `import_source` (otherwise null); export sidecars include it. Geometry is in FreeCAD's internal mm units. Import preserves no original feature history, product hierarchy, names or colors. Surface-only inputs remain native references with `sketch_only` build status and cannot produce a solid export. `capabilities.import_formats` lists STEP suffixes. The bridge requires `request_id` on mutations, including New/Open/Save/Export/Undo; internal human UI calls may omit it. Canonical identical replay returns the original result before stale checking; different-payload reuse rejects. Up to 512 full results are retained, with tombstones for every admitted ID. After 4096 IDs, new IDs reject until reconciliation/restart; old IDs cannot execute again within that session. Expired results reject. Use status lookup or identical replay. `not_recorded` after restart is not proof of nonexecution; no cross-crash exactly-once guarantee. Request cap stays 64 KiB. CLI `send` adds an ID to its caller's dictionary when missing; use explicit persisted IDs in durable retry files.

## Assembly increment — October 2

### Pattern tools

By default a pattern with `operation:"add"|"remove"|"intersect"` applies only its generated copies. The source parts stay separate, and with an automatic scope a source can itself be a target. `include_source:true` gives Onshape feature-pattern semantics: the source parts act as tools together with their copies, and the operation consumes them, as `boolean_parts` consumes its tools. A cutter part patterned ×3 with Remove therefore cuts three holes, and only the target remains. The whole operation is one native transaction and one undo step.

- **Targets.** Source parts are never targets. An automatic scope picks from the other current parts. An explicit `merge_scope` that names a source part, by part ID or by Body name, rejects with `invalid_argument`.
- **Rejections.** `include_source:true` with `operation:"new"` (also the default operation) or `"intersect"` rejects with `invalid_argument`; `false` is accepted. Intersect against several patterned tools is ambiguous (each instance in turn, or their union) and the native multi-tool Common splits its result, so fuse the tools with `boolean_parts` first. A non-boolean value rejects with `invalid_argument`. An automatic scope with no part other than the sources rejects with `empty_merge_scope`. So does an Add whose included source or generated copy touches no target, since Add would discard that solid (`parts` lists those sources, `copies` those copies).
- **Native representation.** The history-bound source snapshots join the copies as `PartDesign::Boolean` tools. The representative records them in `KurtShapePatternToolParts` and records the source part IDs in `KurtShapePatternSourceParts`. `KurtShapeConsumedParts` holds the targets plus the sources. Rollback before the pattern, `delete_features` of it, and undo all restore the source parts. Changing a source's parameters updates every hole. Automatic-scope diagnostics leave the sources out of the target set.
- **Copy ownership.** Since 2026-10-17, pattern copies consumed by Add/Remove/Intersect carry `KurtShapeOperationOwner`, so `delete_features` removes them with their pattern. Before that, a delete of such a pattern failed with `external_dependency`. Copies in older files are found through `KurtShapePatternToolParts`.

### Datum planes

`create_plane` coordinates are world millimetres. They are converted once into the owning Body's frame at creation (the same values when the Body is at identity, which is the normal case). The plane then belongs to the Body and moves with it. Directions need not be unit length; they are normalized. A sketch on the plane (`create_sketch support:{feature:<plane id>}`, no subelement) uses the plane's frame exactly: local +X is the plane's x direction, +Y is normal × x, +Z is the normal, and the origin is the plane origin plus `offset` along the normal. A circle at sketch (10, 5) therefore lies at origin + 10·x + 5·y.

- **Point-normal.** `origin` and `normal` are required. `x_direction` is projected into the plane and rejects when parallel to the normal. When it is omitted, x is world +X projected into the plane, or world +Y when the normal is parallel to X (projection shorter than 1e-6).
- **Three-point.** The origin is the first point, x points toward the second, and the normal is (p2−p1)×(p3−p1), so the third point is on the +Y side. Points closer than 1e-7 mm or collinear points (sine below 1e-7) reject.
- **Line-angle.** The plane contains the line. Its origin is `axis.origin` and x is `axis.direction`. At `angle` 0 the normal is `reference_normal` projected perpendicular to the line, which rejects when parallel to it. A signed `angle` (radians, or a quantity such as `"108 deg"`) turns the plane right-handedly about the line direction. An edge reference or selector supplies the line's origin and direction, from its first-parameter point to its last-parameter point. The edge is copied once at creation and is not tracked afterwards. `PlaneAxisReference` records which edge was used.

Native representation: the offset mode is unchanged. It uses FlatFace on the selected support, and the native expression `AttachmentOffset.Base.z = Offset` drives it. The point-normal, three-point and line-angle modes attach FlatFace to the Body origin XY plane. A native expression drives the whole `AttachmentOffset` from Body-coordinate properties in the "KurtShape plane" group:

- `PlaneMode` (read-only)
- point-normal: `PlaneOrigin`, `PlaneNormal`, `PlaneXDirection`
- three-point: `PlanePoint1`..`PlanePoint3`
- line-angle: `PlaneAxisOrigin`, `PlaneAxisDirection`, `PlaneReferenceNormal`, `Angle`
- every mode: `Offset`

Editing these properties natively moves the plane and the sketches attached to it. Plain FreeCAD rebuilds the saved file without KurtShape. The native attachment editor shows these offsets as expression-bound.

`Offset` is a signed `set_parameter`/`set_expression` parameter for every KurtShape plane. Line-angle planes also report a signed `Angle` parameter in radians, marked `signed:true`.

Inspect adds `plane` to every datum-plane feature, with these fields:

- `mode`: `offset`, `point_normal`, `three_points`, `line_angle`, or `native` for helper planes
- `frame:{origin_mm,x_direction,y_direction,normal}`: in world coordinates; exactly the frame of an attached sketch
- `placement:{position_mm,rotation_xyzw}`: in Body coordinates
- `support` and `map_mode`
- `definition`: the authored request fields in Body coordinates (`origin`/`normal`/`x_direction`, `points`, or `axis`/`reference_normal`/`angle`/`axis_reference`), plus `offset`

Validation rules:

- Fields from two definitions in one request return `invalid_argument` with `modes`.
- Missing required fields, non-finite or boolean numbers, vectors without exactly three components, zero directions and wrong-dimension quantities return `invalid_argument`.
- An edge that is not straight returns `unsupported_axis`, and unknown fields return `unknown_argument`.
- A rejected request leaves objects, Undo and revision unchanged.
- After recompute, the native frame is checked against the request, and a mismatch returns `attachment_failed`.

The GUI Plane tool still authors the offset mode. `preview` accepts every mode, including signed line-angle angles.

### Geometry references and selectors

A geometry reference accepts `{feature,subelement:"FaceN"|"EdgeN"|"VertexN"}` or an authored selector (bare, or `{selector:...}`). Native names remain supported explicit references, not inferred persistent identities. Interactive Use sends the exact picked native edge; Sketcher retains its mapped source association. A native external geometry `Missing` flag produces a `missing_reference` build error and a missing entry in the sketch's `reference_health`, even if Sketcher retains cached geometry and reports its own state as valid. Authored selectors keep their separate query semantics. Selector syntax:

```json
{"kind":"created_by","feature":"Extrude","entity_type":"face","cap":"end"}
{"kind":"owned_by","part":"Body","entity_type":"edge"}
{"kind":"geometry","geometry":"plane","query":{"kind":"owned_by","part":"Body"}}
{"kind":"intersection","queries":[{"kind":"created_by","feature":"Extrude","cap":"end"},{"kind":"owned_by","part":"Body"}]}
{"kind":"closest","point":[10,5,8],"query":{"kind":"geometry","geometry":"plane"}}
{"kind":"geometry","geometry":"circle","radius":17.05,"query":{"kind":"owned_by","part":"Body","entity_type":"edge"}}
{"kind":"geometry","geometry":"torus","major_radius":22,"minor_radius":3,"tolerance":1e-4,"query":{"kind":"owned_by","part":"Body"}}
```

`entity_type` is face/edge/vertex; created-by cap is start/end/side. Set operations are `union`/`intersection` with `queries`, or `subtraction` with `query` and `subtract`. `adjacent` takes `query`, target `entity_type` and edge/vertex `adjacency`; `tangent` expands an edge query. `parallel` takes `query`, `direction` and optional `allow_antiparallel`; `closest` preserves all ties. Geometry filters include plane, cylinder, cone, sphere, torus, line, circle, ellipse, spline and point. Degenerated native edges (sphere poles, cone apexes) report geometry `degenerate` and match no filter. Unknown schema/history rejects. No nth-element selector exists.

A geometry filter can also match native primitive parameters in millimeters: `radius` (positive) for circle, cylinder, sphere and cone, where a cone's radius is the native reference radius at its `axis_point_mm` (it depends on how the cone was built; a cone whose reference circle sits at its apex reports 0 and cannot be radius-filtered); `major_radius`/`minor_radius` for torus and ellipse. All given parameters must match within the absolute `tolerance` (non-negative mm, default `1e-6`). A parameter on a geometry without it (such as `radius` on plane, line or torus), a non-number, zero, negative or non-finite value, or `tolerance` without a parameter rejects with `invalid_selector`; unknown keys reject as for every selector. Stored consumer selectors (fillet/chamfer edges, supports, up-to faces) keep these fields in `QueryInputs` and re-evaluate them at their regeneration position, so a fillet bound to "the radius-5 top circle" follows parameter edits that move or renumber it, and a typed edit that leaves no such circle rejects with `build_failed` instead of substituting another edge. Radii are read through the selector's cached native scalars.

`resolve_selector` returns each match's `summary`: `geometry`, `center_mm` (centre of mass), `area_mm2` (faces) or `length_mm` (edges), `normal` (planes), plus usable geometry for picking without outside math:

| Element | Added summary fields |
|---|---|
| every edge | `point_mm`: the point at the edge's mid-parameter, on the edge |
| line edge | `direction`: unit vector from the first-parameter to the last-parameter point |
| circle/arc edge | `radius_mm`, `geometric_center_mm`, `axis` (unit native curve normal) |
| ellipse edge | `major_radius_mm`, `minor_radius_mm`, `geometric_center_mm`, `axis` |
| every face | `point_mm`: a point on the face clear of its boundary: the parametric centre when it lies inside the face, otherwise the nearest inside point of a parameter grid, the projected centre of mass, or a point stepped inward from an edge midpoint (last resort: the longest edge's midpoint) |
| cylinder face | `radius_mm`, `axis`, `axis_point_mm` (native axis location) |
| cone face | `radius_mm` (reference radius at `axis_point_mm`), `axis`, `axis_point_mm`, `apex_mm`, `semi_angle_rad` |
| sphere face | `radius_mm`, `geometric_center_mm` |
| torus face | `major_radius_mm`, `minor_radius_mm`, `geometric_center_mm`, `axis` |

`center_mm` keeps its centre-of-mass meaning (for an arc it lies off the edge); use `point_mm` as a `closest` pick point. A `closest` selector at a reported `point_mm` with the same query returns that element alone for non-degenerate edges and for faces whose point lies clear of the boundary (not the last-resort edge midpoint). Faces OCCT keeps as surfaces of revolution report geometry `surfaceofrevolution` and have no parameter filter. `ambiguous_reference` errors list their `matches` with the same detailed summaries. These detailed fields are computed only for that read output and ambiguity diagnostics, never while consumers rebind during a rebuild.

Consumers store `QueryInputs` on their native feature and evaluate at that feature's regeneration position, after dependencies and before consumer recompute. Native resolved links are caches. Rebinding, input health and a bounded `QueryResolutionLog` occur inside the mutation transaction. Health is healthy/missing/ambiguous; unknown history is missing with its error code. A missing or ambiguous reference retains the last native link and never substitutes another element. Such intent has no current measurements and blocks export. A rejected typed edit rolls back; unresolved intent introduced through native editing remains visible until repaired. Evaluation compares the actual native property with the selector result, so manually changed native links cannot remain healthy merely because their JSON cache still matches. Ordinary inspection detects cheap native-link divergence; after external native recompute, sync reconciles exact derived health outside the observer callback without a nested rebuild or authored-link write. Changed resolution requires managed Rebuild, which restores the authored query. Idle inspection reads cached health without query evaluation.

Created-by traces the pinned FreeCAD 1.1.4 raw element-name branches and explicit native whole-part generator metadata, distinguishing generated/modified topology and retaining all tested refined merge ancestors. Unsupported hashed, stale or unknown maps fail closed. Caps use native extrusion/revolution/loft/sweep geometry; this is local OCCT lineage, not an Onshape topology-ID translation. GUI geometry picks author ownership, geometry and closest-point predicates explicitly; a tie becomes ambiguous. Native link/constraint parameters remain authoritative. Diagnostics records selector evaluation separately from total rebuild. See [carrier evidence](architecture-responsiveness-upgrade/STATUS_REPORT.md#baseline-foundation), [parity limits](ATLAS_PARITY.md) and [walkthrough](U2_WALKTHROUGH.md).

### Multi edge references

`fillet`, `chamfer` and `edit_dress_up` accept, as any entry of `edges`, the explicit multi reference `{"selector":<query>,"all":true}`. It stands for every edge of the current part (the feature's input) that the query matches, so one entry can express a group such as all rims between two face sets:

```json
{"op":"fillet","radius":1,"edges":[
  {"selector":{"kind":"geometry","geometry":"circle","radius":3,"query":{"kind":"owned_by","part":"Body","entity_type":"edge"}},"all":true},
  {"selector":{"kind":"intersection","queries":[
     {"kind":"adjacent","entity_type":"edge","query":{"kind":"geometry","geometry":"cylinder","radius":22,"query":{"kind":"owned_by","part":"Hub"}}},
     {"kind":"adjacent","entity_type":"edge","query":{"kind":"geometry","geometry":"torus","major_radius":31.464,"query":{"kind":"owned_by","part":"Hub"}}}]},"all":true}]}
```

- **Meaning.** Matches that are not edges, or not on the current part (sketch edges, other parts), are ignored. At creation at least one edge must remain, otherwise `missing_reference`. Without `all`, or with `all:false`, an entry keeps its single-element meaning: it must resolve to exactly one edge (`ambiguous_reference` with detailed `matches` otherwise).
- **Mixed lists.** Literal references, single selectors and multi references can be mixed. The native `Base` lists the entries in request order, each multi entry's edges in native index order, and an edge already listed by an earlier entry is kept once, at its first position (no duplicate rejection in such a list). A list without any `all:true` entry keeps the per-slot binding described above, byte for byte.
- **Regeneration.** Every entry of such a list becomes a `QueryInputs` member `edges_<i>` with mode `linksub_group`, `index` (entry position), `many` (true for multi), `entity_type`, `slots` (the `Base` positions it owns after de-duplication) and `resolved` (the edges in those slots). Literal members carry `literal:true` and keep their edge: while the native list keeps its recorded layout, they take the name FreeCAD's element tracking holds in the slot that carries the edge, which is their own slot, or, for a literal whose edge an earlier entry already includes (no slot of its own), that entry's slot (`element_slot`). They also record the edge's FreeCAD mapped name (`mapped`), resolved on the current input when the layout no longer matches; a mapped name that no longer resolves makes the literal `missing`. So a de-duplicated literal re-enters `Base` at its own edge after renumbering when the earlier entry stops including it. At each managed regeneration, after dependencies and before the consumer recomputes, every selector member is evaluated again and the whole `Base` list is rebuilt from all members in order, so a multi entry's range grows or shrinks (`QueryResolutionLog` records each member whose edges changed). If any member is missing or ambiguous, the complete last native list is kept; nothing is rewritten or substituted, and only that member is reported (its healthy siblings are not reported as pending even when FreeCAD's tracking renames the kept list).
- **Health.** A multi member's `count` is its matched edges. A multi entry that later matches nothing is `missing`: the typed edit that causes it rejects with `build_failed` and rolls back; a native edit outside a managed transaction leaves a failed build that blocks export until repaired. A native edit that changes a group's matches reports `pending_selector_resolution` until managed Rebuild rewrites `Base`. Save/reopen, undo/redo and studio rollback keep the members with the native list.
- **Rejections** (nothing changes): `all` on a literal reference or beside a bare query (`{"kind":...,"all":true}`), a `selector` that is not a query object, or non-boolean `all` reject with `invalid_argument`; other keys in the wrapper reject with `unknown_argument`. In a list that contains a multi reference, a single `{selector:<query>}` wrapper may hold only `selector` and `all`, and any other key (for example a mistyped `All`) rejects with `unknown_argument`; literal references and bare queries are checked as in a plain list (`invalid_selector`).
- **Editing.** `describe_dress_up` reports a multi member's slots with the reference `{selector, all:true}`, labelled with the member's match count. An entry that owns no slot because earlier entries already include its edges is reported as one extra row with `subelement:null` at its entry position. Sending the distinct references back in row order therefore reproduces the authored list, including such entries. A de-duplicated literal whose edge no longer exists is left out of the rows and named in `limitations` instead of being returned as a stale element name. Editing to a list without multi references returns to per-slot binding.

### Viewport camera: `set_view` (GUI, 2026-10-20)

`set_view` points the running app's 3D view of a document at part of the model. It is the second **view operation** (`VIEW_OPS`, beside `render_view`): it changes only the GUI camera, never the document, its revision, undo history, Modified flag or `LastFailure`; it is allowed on unmanaged documents; through the bridge it is ledger-tracked (`request_id` required); `expected_revision` is optional and checked when given (`stale_revision`). It is refused while a sketch or native feature edit is active (`sketch_edit_active`), and it is not previewable or batchable.

```json
{"op": "set_view", "document_id": "<id>", "request_id": "agent-0012",
 "view": {"direction": [0.8303, -0.329, 0.4498], "up": [0.2692, -0.4698, -0.8407]},
 "frame": {"center_mm": [-369.286, -233.18, -5.349], "width_mm": 14}}
```

| Field | Values | Default | Rules |
|---|---|---|---|
| `view` | `iso`, `front`, `back`, `right`, `left`, `top`, `bottom` (the `render_view` directions), or `{direction:[x,y,z], up?:[x,y,z]}` | `iso` | the camera looks along `direction`; `up` points to the top of the window (default +Z, or +Y when the direction is within 2.6° of ±Z); nonzero and not parallel (`|cos| < 0.999`) |
| `frame` | `model`, or `{center_mm, width_mm}` | `model` | `model` centres the box of the shown top-level solids and faces and spans its projection with a 5 % margin; an explicit `width_mm` spans the window's **shorter** side, so the whole square is visible in any window shape |

The camera is orthographic. It stands in front of everything shown (so nothing between it and the frame is clipped), its focal point is the frame centre (the rotation centre for navigation styles that use it), and its `height` is the frame width.

**Response.** `{document_id, revision, view, frame, applied, reason, camera, note}`. `camera` is `{projection, direction, up, right, center_mm, height_mm, distance_mm}`; in the app it is read back from the view after the change. `applied:false` with `reason:"no_gui"` comes from the headless Controller, which has no 3D view and only computes the camera; `reason:"no_view"` means the document has no 3D view open.

**Persistence.** FreeCAD writes a document's camera into the FCStd (`GuiDocument.xml`) on every save made with the GUI up and restores it when the file is opened, including through the bridge's `open` (which adds no fit afterwards; the GUI's own Open and recent-file actions still switch to isometric and fit). So a camera set in a hidden app (`tools/assistant.ps1 -Hidden`) before `save` is the view the user sees when the saved file opens in their app. A file saved headless has no `GuiDocument.xml` and opens with FreeCAD's default camera.

Tests: `tests/test_gui_view.py` (`GuiViewTests`: headless camera, rejections, revision and undo unchanged, Inventor camera text round trip). The GUI application path was checked by hand on 2026-10-20 (`projects/dodec-hub`, the example above): in a hidden app `set_view` reported `applied:true` with the camera read back from the view, `save` wrote it to `GuiDocument.xml`, and an offscreen FreeCAD that opened the file with `App.openDocument` restored the same camera. There is no automated GUI recipe for it yet.

### Finish cost, compact mutation responses and `preview` as a read (slice A/B U6, 2026-10-22)

**One managed recompute per Finish (A2).** `finish_sketch_edit` runs exactly one managed recompute (one `native_recompute`, one `selector_evaluation` and one `managed_rebuild` timing event), one native build check and one edit-mode result validation, whether the lease holds one native transaction or several. Several native commands in the lease are regrouped *before* that recompute (the lease's commits are undone and the final sketch content is restored inside the one grouped transaction), and the group is counted through the document observer's commit count rather than `UndoCount`, so a grouped Finish is one undo step even after FreeCAD's undo stack is saturated (on a headless `App.Document` the stack holds 20 steps and nothing in Python raises it). A build failure or a result-check rejection still keeps the lease and the draft (`_preserve_sketch_draft`); after a regrouped failure the lease continues in one pending native transaction holding the draft (the managed `undo`/`redo` snapshots are unchanged). The report-mode validation that settles and persists verdicts after the lease is unchanged (it is cached-key work, no recompute). A failed ungrouped Finish now commits the lease's pending step into native history before failing (one `KurtShape: edit` step; the lease continues in a fresh pending transaction holding the draft, and retry, Finish and undo still end correctly); a failed regrouped Finish aborts its grouped transaction. Native undo and redo inside the lease (Std_Undo/Std_Redo) are counted beside the commits, so the regroup undoes exactly the lease's steps and never an accepted pre-lease transaction; more undos than lease steps reject with `sketch_history_changed`. The controller also raises FreeCAD's undo-step preference (`User parameter:BaseApp/Preferences/Document/MaxUndoSize`, read when a GUI document is created) to at least `UNDO_STEPS` (200), once per process, and never lowers it; the preference persists in the profile's user.cfg. FreeCAD's `UndoMemSize` preference does not bound it: in `src/App/Document.cpp` (FreeCAD main, read 2026-10-22; 1.1.4 not checked separately) `_commitTransaction` pops one entry past `UndoMaxStackSize` and `UndoMemSize` is only stored and reported through `getMemSize()`, so the stack's memory is the step count times the transactions' size; the cost of 200 steps on a large document is unmeasured. Pinned by `FinishRecomputeTests`. The GUI runs one inspection per committed action: the mutation's own response is the panel state, the pre-operation inspect became a cheap `sync` (the current revision), and the observer's `refresh` flag is honoured once per action. Evidence: the `inspection-count` GUI recipe (`tools/inspection-count-validation.FCMacro`) spies the real Controller around each committed action (sketch, pad, parameter edit, undo, a GUI sketch begin → Finish) through the two ticks that follow and asserts exactly one inspection and no `inspect` dispatch per action. Bridge mutations and native edits are unchanged (dispatch inspection plus the tick's inspect and refresh); quiet reads keep the E-08 skip.

**Compact mutation responses (B1).** Every mutating operation (model, assembly, create, lifecycle `save`/`export`/`adopt`, history, `batch`; not the reads, not the view ops, not `close_document`) takes `detail`:

| `detail` | Response `result` |
|---|---|
| omitted | the full inspection **without** `operations` and `last_failed_attempt` (both still in `inspect`; `detail:"full"` returns them) plus `created_feature`, `batch_report`, `geometry_check_report` and the per-request reports, as before |
| `"full"` | the full inspection exactly as `inspect` returns it, plus the same additions |
| `"compact"` | the compact header of `list_documents` (`document_id`, `revision`, `name`, `native_file`, `modified`, `modified_basis`, `unsaved`, `managed`, `build_status`, `rebuild_reason`, `build_errors`, `geometry_check`, `active_sketch_edit`, `detail:"compact"`, `result_checks`, `studio`, `feature_count`, `part_count`) plus `created_feature`, `batch_report` (with its `created_features`) and the per-request reports (`result_check_report`, `result_report`, `repair_report`, `parameter_report`, `changed_inputs`, `created_parameter`), and `operation_ms`; no feature, part or parameter rows (about 1 KB on a 13-cut part against 20–90 KB full) |

A value other than `full`/`compact` rejects with `invalid_argument` (`fields:["detail"]`) before anything runs; `null` counts as omitted; errors are unchanged. `inspect` and `list_documents` keep their own `detail`. A `detail` inside a batch step or a preview proposal is not an argument of the step and is ignored. The next request's `expected_revision` is the compact header's `revision`. Pinned by `CompactResponseTests`.

**`preview` is a true read.** `expected_revision` is optional for `preview` (a read operation, `read_operations`, never ledgered): omitted, the proposal is evaluated against the current document and `base_revision` reports that revision; given, it must equal the current revision (`stale_revision` otherwise). The schema no longer requires it (`x-mismatch-code: stale_revision`, like the view ops); `kurtshape.session` still sends it (`REVISION_ALWAYS`, harmless). Pinned by `CompactResponseTests.test_preview_without_a_revision_evaluates_the_current_document`.

### Save safety and recovery checkpoints (slice A/B U8, 2026-10-22)

**`save` never silently replaces another project's file (A8).** When the destination exists, `save` reads the KurtShape project id stored in it (its `Document.xml`, streamed, about 10 ms on a 10 MB project; nothing is opened) and proceeds only when it is this document's `document_id`: the document's own file, or any other copy of the same project. A destination that holds another project, a native FreeCAD file without KurtShape metadata, or a file that is not a readable FCStd (not a ZIP, a corrupt deflate stream, broken XML) rejects with `save_destination_other_project` (`path`, `existing_document_id` (null when there is none), `existing_project` (the stored document label, or null)); the message names the file and the project, the file is byte-identical afterwards, and nothing else changes. `overwrite:true` (new boolean argument, default false; any other type rejects with `invalid_argument`, `fields:["overwrite"]`) replaces it; a new path needs no flag. The GUI's Save As passes `overwrite:true` after its own Save dialog asked about replacing; its Save to the document's own file does not.

**A locked or read-only destination is a typed error (A8).** Any OS error while reading the destination for that check, copying it to `<name>.recovery.FCStd`, or replacing it rejects with `save_destination_locked` (`path`: the destination, `reason`: the OS reason such as `Permission denied`, `file`: the file the OS named when it is neither the destination nor the stage, for example a locked recovery copy); the message names the file. The previous file is unchanged, the `<name>.saving.FCStd` stage is removed on every outcome (a failed native write included; a stage that cannot be removed is never ignored: the error gains `stage` and `stage_cleanup_error`, a successful save reports them in a `save_stage` block, and the log gets a warning), the document keeps its previous `native_file`, and the same `save` succeeds once the lock is gone. The recovery copy is written with the destination's contents and times but not its read-only attribute (a copied attribute blocked every later save).

**The "Saving…" hook (A4).** `Controller.recovery.stall_status` (default None) is called with `"Saving…"` immediately before `save`'s native write (also for `adopt` and Save As) and with `"Checkpoint…"` before a recovery checkpoint's native write, and with `None` when the write is done (also after a failure). The GUI binds it to paint the status line and the footer at once (`QWidget.repaint`, no event-loop pass), so the synchronous stall is announced before it starts; headless callers leave it unset.

**Recovery checkpoints write faster with identical contents (A4).** A checkpoint archive is written with FreeCAD's `Preferences/Document/CompressionLevel` at 1 for that one `saveCopy` (restored afterwards; session `settings.json` `"recovery_fast_snapshots": false` keeps FreeCAD's level). Every restored BRep is byte-identical to a default-level archive and the strict native snapshot of the reopened file is equal. Measured headless, pinned (`0xFFFF`), medians of six interleaved `saveCopy` runs, default → level 1: plate60 806 → 710 ms, studio fixture 84 → 75 ms, Dodec Hub copy 2,297 → 1,314 ms (1.75×); forced checkpoint (write + verify + publish), three interleaved runs each: Dodec Hub 2,606 → 1,621 ms (1.61×), plate60 775 → 789 ms and studio 138 → 142 ms (no measurable change on the small fixtures); archives 16–40 % larger. `SaveBinaryBrep` was measured too (plate60 806 → 462 ms, Dodec Hub 2,297 → 726 ms) and **not adopted**: a restored binary archive differs from the text one in the TShape `Checked` flag on every fixture and, on the Dodec Hub, in location matrix digits at 1e-16 (the text format writes 15 significant digits), so the strict snapshot is not identical. Publication (ZIP check, hash, replace) stays on the recovery executor for idle checkpoints. Preview snapshots are unchanged. Pinned by `SaveSafetyTests` and `RecoveryPolicyTests`.

**FreeCAD's autosaver (decision 3).** `ui.start` sets `Preferences/Document/AutoSaveEnabled` false (it set it true with a one-minute timeout since 5f91ba2), so KurtShape's checkpoints are the one recovery writer; `"keep_freecad_autosave": true` in the session's `settings.json` keeps FreeCAD's one-minute autosaver. FreeCAD applies the value at its next start.

The document is unchanged; the Confirm gate remembers the code like `empty_cut`.

**One direction vocabulary (B2).** `pad`, `pocket` (legacy and studio) and `hole` accept `direction: "along" | "against"`: the side of the profile normal (a sketch's +Z; for a studio `face` extrusion, the face's outward normal) the tool runs to.
